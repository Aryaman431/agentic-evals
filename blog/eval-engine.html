How the Evaluation Engine Was Built

Engineering · 8 min read agentic_evals

Every use case on this site - the chatbot, the voice agent, the release gate - eventually bottoms out in the same place: a small evaluation engine that turns a recorded trace into a score, a score into a verdict, and a verdict into a pass or fail. This post opens that engine and describes the pieces that make testing an agent feel like testing software.

Why an agent is not a function

The instinct when teams start evaluating agents is to reach for the tooling they already have for ordinary software: call the thing, assert on the output, move on. Agents resist this framing because they do not have an output you can assert on. What they produce is behaviour - a plan, a tool call, a sentence, a decision - and the behaviour is shaped by reasoning that never appears in any single place you can point at.

That is why the failures hide in the seams. The reasoning step is fine but the tool call is wrong. The tool call is right but the argument is corrupted. The answer is fluent but the claim is unsupported. A single assertion cannot see any of that, because none of it is a property of the final answer alone. The evaluation has to observe the run, not just the result.

The consequence is that evaluation has to be built as a small system of its own: capture a trace, score the trace, and turn the score into a verdict. Everything else on this site is an instance of that pattern.

The trace is the contract

The engine core data model is deliberately small. An EvalTrace holds a trace identifier, the EvalSpans that make it up, total latency, an estimated cost, and metadata. An EvalSpan holds a tool name and a bag of attributes. That is the whole shape the engine inspects.

The design note worth reading closely: the engine does not adopt any vendor trace schema. It does not inherit AgenticLens's richer Span, with agent names, retries, timestamps, and everything else. The engine only needs the pieces it actually uses, and by keeping the contract narrow it can consume any trace-shaped data a team already has. You can produce an EvalTrace without depending on a specific tracing tool schema at all.

A narrow contract is a decision, and it is the kind of decision that ages well. Tracing vendors will keep adding fields. The evaluation engine should not care.

One interface, many scorers

Scoring is expressed through a single interface with multiple implementations: text scorers, trajectory scorers, and rubric scorers that use a language model as the judge. Every score carries a value between zero and one, a pass flag, whether it is required, and a human-readable explanation of why it passed or failed. That last field is not decoration; it is what turns a number into something an engineer can act on.

Scorers are then bundled into packs through test cases. A test case declares what the behaviour was expected to be: an expected output, a set of substrings that must appear, a JSON schema for structured output, required or forbidden tools, the arguments a tool call should carry, latency and cost ceilings, turn limits, and the evaluators that judge it. A test case that declares no expectation at all is rejected, so an empty case cannot silently become an unchecked case.

The pack model is what keeps evaluation honest as the surface area grows. Instead of one monolithic rubric written once, expectations are expressed per behaviour, and evaluators are attached to the cases that need them.

From scores to a decision: the gate

A score is not a verdict. The engine gate takes a full evaluation report and turns it into a decision with reasons. The gate configuration carries the thresholds a team cares about: minimum pass rate, minimum average score, maximum failed cases, maximum average latency, and maximum total cost. The decision returns a pass flag plus a list of reasons explaining what failed, plus the observed numbers it decided against.

That separation matters. Keeping the thresholds in configuration, and keeping the decision's reasoning alongside the observed values, means the verdict can be reproduced and audited later. A pass flag without reasons is a dashboard. A pass flag with reasons is a decision.

Running evals in CI

The command line entry point discovers evaluation files by convention, runs them, and exits non-zero if any case failed. The conventions mirror what teams already know from testing: files named to match, a runner that collects results, and an exit code that a CI pipeline can act on without parsing prose.

That last point is the quiet hero of the design. Every evaluation on this site can be run headlessly, printed to a scorecard, and gated behind a threshold. The same engine that powers the interactive playgrounds also powers the automated verdicts.

Lessons

  • Contracts beat cleverness. The narrow trace contract did more work than any abstraction.
  • Separate scoring from deciding. A score is data; a gate is policy.
  • Require expectations. An evaluation without one is not an evaluation.
  • Make reasons first-class. A verdict without a why is a feeling.

Takeaway

The engine is deliberately boring. Small contracts, one scorer interface, explicit gates, and an exit code for CI. Boring is exactly what you want in something that runs on every release and has to be trusted by the people shipping the agent.

Run it from the repository root: agentic-evals run discovers and runs every eval file in the current directory - agentic-evals run evals/ scopes it to a folder - the CLI exits 0 when all cases passed and 1 when any failed, which is what makes it CI-ready.
