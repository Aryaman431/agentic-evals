Chatbot Evaluation

Beginner · 8 min read Chatbot-eval

Maya types two sentences into a support chat and gets two instant answers. Both sound perfect. This article opens the box between her message and the reply, then shows the ten test cases and eight rules that decide whether what came out was actually right.

The problem

Maya ordered a birthday gift for her sister. The delivery date passed, the tracking never updated, and at 11 p.m. she opens the company's support chat. She types: “Where is my order 1234?” A second later the bot replies that the order shipped and gives her a date. She types: “I want a refund for order 1234.” Another second, another confident reply.

Here is the uncomfortable part: from the outside, a correct answer and a confident guess look identical. Nothing in that chat window tells Maya whether the bot actually looked up order 1234, or whether it pattern-matched her sentence and produced something that sounds like an answer.

It gets worse when you zoom out. One chatbot serves thousands of people at once, and the answers that go wrong go wrong quietly. A refund issued against the wrong order. A cancellation that never happened. A delivery date invented out of thin air. Nobody files a bug report — they just stop trusting the company.

So the question is not “does the chatbot sound good?” The question is: how would we know? Reading one reply by eye cannot answer that, because you would have to already know the correct answer. What we need is a way to check the reply against something written down first.

The approach: write the expectation down first

Agent evaluation is a simple idea with a fancy name: before you run the agent, write down what each exchange is supposed to do. Then run it. Then compare what it actually did with what you wrote. The comparison is mechanical, so it gives the same answer every time — and it can run a hundred times without anyone getting bored.

Five words carry most of the weight, so let us define them once, properly:

  • Test case — one input plus the behaviour we expect back. Maya's refund case is the sentence I want a refund for order 1234. plus the expectations: intent refund_order, tool refund_order, and a reply that contains the word “refund”.
  • Intent — the label the agent concludes the user wants. This project uses four: order_status, cancel_order, refund_order, and unknown for anything out of scope.
  • Tool — a small program the agent is allowed to call, the only way it can touch real data. This project ships three: get_order, cancel_order, and refund_order.
  • Trace — a recorded timeline of one run: the message that went in, the intent that was detected, the order id that was extracted, the tool that was called with which arguments, the reply that came out, and how long it took. Everything the evaluators need lives in the trace.
  • Evaluator — a rule that reads a trace and returns pass or fail with a short explanation of why. Evaluators are where “we think it works” turns into “rule 4 says it works”.

Notice what writing the expectation down buys us. The expectations exist before the run, so the answer gets judged instead of admired. A single case only proves one path, so we keep a suite of cases that covers the boring paths too — the missing order number, the nonsense request, the cancellation. And because each rule is separate, a failure tells us which stage broke instead of just “it was wrong somehow”.

There is one more trick, and it is the most convincing one: fault injection. We deliberately break one stage of the agent on purpose — swap the tool, corrupt the order id, append a claim the data does not support — and then check that the matching rule actually fires. A rule that never fires when you break things on purpose is decoration, not a check.

How the evaluation works

Every message travels the same road inside the project. The message goes into a transcription step (simulated — it returns the text unchanged, kept so this project and the voice project share the same shape), then keyword-based intent detection picks one of the four labels, then the order id is pulled out of the sentence, then a tool is selected, and finally the reply is written from whatever the tool returned.

Eight rules judge the result. Each one looks at a different stage, so each one can fail independently:

  1. Transcript Accuracy — did the text that entered the pipeline match the text the case expects?
  2. Intent Accuracy — was the detected intent the label the case requires?
  3. Tool Selection — was the required tool the tool that actually ran?
  4. Tool Arguments — did the arguments survive the trip, order id 1234 and not 12340?
  5. Response Quality — does the reply contain what the case asks for, such as the word “refund” or the string September 28?
  6. Groundedness — can every factual claim in the reply be traced back to what the tool really returned?
  7. Reliability — did the run finish without errors, and did the agent ask instead of guessing when information was missing?
  8. Latency — did the whole thing finish inside the time budget?

Groundedness is the one worth pausing on, because it is the rule that catches the polite lie. It takes the words in the reply that make factual claims — shipped, delivered, processing, cancelled, refunded, tomorrow, today — and checks each one against the tool's real result. If the tool said “shipped, ETA September 28” and the reply says “it will arrive tomorrow”, the word tomorrow has no evidence behind it, and the rule fails.

A simple example

Three exchanges, all built from the project's own mock data. Order 1234 is shipped with an ETA of September 28, order 5678 is still processing with an ETA of October 2, and order 9999 has already been delivered. The chips under each reply are what the evaluators would print.

Attempt 1 — the agent picks the wrong tool

Maya asks for a refund. The intent detection gets it right (refund_order), but the fault injection rotates the tool one step, so refund_order becomes get_order. The agent dutifully reports on her shipment instead of refunding anything.

Maya — I want a refund for order 1234.

Agent (fault: wrong_tool) — Order 1234 has shipped. It will arrive on September 28.

Fail · Tool Selection Fail · Response Quality — no “refund”

Two rules fail for two different reasons, and that is the point: Tool Selection says the wrong program ran, Response Quality says the reply never answered her question. Maya would have just typed again, annoyed.

Attempt 2 — the agent does it properly

Same message, no fault. The intent is refund_order, the tool is refund_order, the argument is order_id: "1234", and the reply is built from what the tool returned.

Maya — I want a refund for order 1234.

Agent — I've started a refund for order 1234. It will be returned to your original payment method.

Pass · Tool Selection Pass · Tool Arguments — order_id 1234 Pass · Response Quality — contains “refund”

Attempt 3 — a correct answer with one invented sentence

This is the failure a human reviewer misses most often. Everything above is right, and then the agent adds a friendly promise that no data supports:

Maya — Where is my order 1234?

Agent (fault: unsupported_claim) — Order 1234 has shipped. It will arrive tomorrow.

Pass · Tool Selection — get_order Fail · Groundedness — “tomorrow” not in the tool result

The tool result for order 1234 says shipped, ETA September 28. The word tomorrow appears nowhere in it, so Groundedness fails even though every other rule passes. One polite sentence, one broken promise, one rule whose whole job is to notice.

What the actual project demonstrates

Everything above runs inside Chatbot-eval/ in this repository. It is a simulated text customer-support agent: no real payments, no real orders, no external services. The dataset is ten cases, and each case checks exactly one thing so a failure points at one stage.

Test case Input What it checks
stt-basic Where is my order 1234? The transcript step passes a plain sentence through unchanged
stt-accent Can you track order 5678? The same, with accented wording in the input
intent-status Where is my order 1234? Detected intent is order_status
intent-cancel Please cancel order 5678. Detected intent is cancel_order
intent-refund I want a refund for order 1234. Detected intent is refund_order
tool-selection Where is my order 1234? The tool that ran is get_order
tool-arguments Where is my order 1234? The argument that reached the tool is order_id: "1234"
task-completion Where is my order 1234? The reply contains 1234, shipped, and September 28
missing-order Where is my order? With no id given, the reply asks for the “order number” instead of guessing
unknown-intent Tell me something interesting. Intent is unknown and the reply says it “didn't understand” — no order tool called

On top of the dataset, the project ships nine fault modes — normal plus eight deliberate breakages — and each one names the rule that is supposed to catch it. This table is the project's own fault-to-rule mapping:

Fault injected What it does Rule that catches it
wrong_intent Intent label swapped after detection Intent Accuracy
wrong_tool Intent kept, but a rotated tool runs with the same arguments Tool Selection
wrong_arguments Extracted order id corrupted (1234 → 12340) Tool Arguments
hallucinated_response Reply claims delivered/tomorrow regardless of the tool output Groundedness
unsupported_claim Correct reply with “It will arrive tomorrow.” appended Groundedness
tool_failure Tool returns an error payload instead of a real result Response Quality
missing_information Order-id extraction forced to fail; the agent must ask Reliability
slow_response A real 250 ms delay against a 100 ms budget Latency

What you can open and click

The frontend has three working views. A Chat Playground, where a typed message is posted to POST /chat/evaluate and comes back with the response, the detected intent, the tool, the arguments, and the latency. A Scenario Lab, which runs a chosen scenario live through the full chain — Evaluation API → agent → evaluation → trace → metrics → dashboard — so you can watch a fault get caught in real time. And views for the 10-case dataset and for the evaluation report of each run.

The backend is FastAPI in Chatbot-eval/server.py, port 8001, with the endpoints /health, /scenarios, /dataset, /evaluate, /chat/evaluate, /runs, and /stats. Run history lives in memory: there is no database, so a restart clears it. Opened statically, without the backend, the page still loads and shows an offline status rather than pretending to work.

There is also a command-line path for people who never want to open a browser: run_evals.py builds a test suite from the ten cases, runs the agent against each one, prints a scorecard with per-metric pass rates, and exits with code 0 when everything passed and 1 when something did not — which is what makes it usable in a CI job.

Limitations

This is a teaching project, and it is honest about the seams. The transcription step is simulated — it hands the text straight back unchanged — so nothing here proves anything about real speech recognition. Intent detection is keyword matching, not a language model, which makes it fast and deterministic but easy to fool with an unusual phrasing. The dataset is ten synthetic cases, not a sample of real customer traffic, and the mock orders are three dictionary entries.

Simulated pipeline. The “speech-to-text” step returns its input unchanged, and the dataset keeps the legacy audio and transcript field names it shares with the voice project — so a field called audio here contains plain text. Latency is measured on your machine against a local mock, which tells you about this code, not about production traffic.

Takeaway

A chatbot that sounds right is an opinion; a chatbot that passes ten written cases is a measurement. Write the expectation down before the run, give every stage its own rule, and break the agent on purpose to prove the rules fire.

Run it from the repository root: python Chatbot-eval/run_evals.py prints the scorecard and exits 0 or 1 · python Chatbot-eval/server.py starts the backend on port 8001 for the Chat Playground and Scenario Lab · without the backend the page opens statically and shows an offline status.
