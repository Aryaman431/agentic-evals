Voice Agent Evaluation

Beginner · 8 min read voice-agent-evals

A phone call has no undo button and no “show me your work” link. Priya says one sentence, and five things have to go right in a row before she hears a true answer. This article walks the whole chain, then shows the rules that tell you which link broke.

The problem

Priya calls the support line about a birthday present that never arrived. “Where is my order 1234?” she says, half-listening to a toddler in the background. For her to hear a useful answer, the system has to do five things in a row: hear her words correctly, work out what she wants, pick the right action, run it with the right order number, and say something true back.

Five things in a row means one thing: the call is a chain, and a chain fails at its weakest link. If the speech step hears “order 12340” instead of “order 1234”, nothing downstream can save it. If the intent step hears “cancel” when she said “track”, the agent will happily cancel an order she wanted to watch. If the reply adds “it will arrive tomorrow” when nobody promised that, she will stop trusting the whole company over one sentence.

And unlike a chatbot, a voice call is hard to review after the fact. There is no screenshot to forward to a colleague, no obvious place to pause and think. Either the caller got a correct answer inside a couple of seconds, or she hung up. That is exactly why the checking has to happen automatically, on every path, before anyone relies on it.

The awkward truth is that a single good call proves very little. The agent can handle the easy question perfectly and still mishandle the cancellation, the missing order number, or the request that has nothing to do with orders at all. One call is an anecdote. A suite of calls is evidence.

The approach: test every link separately

Agent evaluation means writing down what each call is supposed to do before you run it, running the agent, and comparing the two mechanically. Because the expectations are written first, the result gets judged instead of admired — and because the comparison is mechanical, it gives the same answer every time you run it.

The five words you need, defined once:

  • Test case — one input plus the behaviour we expect back. For “Where is my order 1234?” the expectations are: transcript unchanged, intent order_status, tool get_order, argument order_id: "1234", and a reply containing the words the case asks for.
  • Intent — the label the agent concludes the caller wants. This project uses order_status, cancel_order, refund_order, and unknown for anything out of scope.
  • Tool — a small program the agent is allowed to call, and the only way it can touch real data: get_order, cancel_order, or refund_order.
  • Trace — a recorded timeline of one run: what was heard, what was decided, which tool ran with which arguments, what was said back, and how long it took. Every rule reads the trace, so nothing is judged from memory.
  • Evaluator — a rule that reads a trace and returns pass or fail with a one-line reason. One rule per link, so one failure names the link.

The chain structure is what makes this work. Because each stage hands its output to the next one, you can put a checkpoint between every pair of stages and ask a narrow question: did the text survive? was the label right? did the right tool run? was the id intact? is the reply supported by the data? did it finish in time? Narrow questions have narrow answers, and a narrow answer tells an engineer where to look.

Then comes the part that proves the checks are real: fault injection. The project deliberately breaks one stage at a time — swap the tool, corrupt the order id, append an unsupported claim, sleep for 250 ms — and verifies that the matching rule is the one that complains. If breaking a stage does not make its rule fail, the rule is decoration.

How the evaluation works

The pipeline mirrors the call itself. The caller's words go into a speech recognition step, the text goes to intent detection, the order id is pulled out of the sentence, a tool is selected and called, and the reply is written from what the tool returned. Only then does evaluation run — over the whole trace, not over the final sentence alone.

Eight rules judge the result, one per link plus two for the answer itself:

  1. Transcript Accuracy — did the text that entered the pipeline match the text the case expects?
  2. Intent Accuracy — was the detected intent the label the case requires?
  3. Tool Selection — was the required tool the tool that actually ran?
  4. Tool Arguments — did the order id reach the tool intact?
  5. Response Quality — does the reply contain what the case asks for?
  6. Groundedness — can every factual claim in the reply be traced to what the tool really returned?
  7. Reliability — did the run finish without errors, and did the agent ask for the missing order number instead of guessing one?
  8. Latency — did the whole thing finish inside the time budget? One scenario sets that budget at 100 ms on purpose.

Latency deserves a note, because it is the one rule where the fault is not a lie but a delay: the slow_response fault inserts a real 250 ms sleep inside the timed section, against a 100 ms budget. Nothing is faked — the clock genuinely runs over, and the rule genuinely fails.

  1. 01 Caller Speaks Priya says her line into the phone. →
  2. 02 Speech Recognition Her words become text — accents included. →
  3. 03 Intent The agent decides what she is asking for. →
  4. 04 Action It calls the right tool with the right order number. →
  5. 05 Evaluation Eight rules read the trace and check every link in the chain.

A simple example

Three moments from Priya's call, using the project's own mock orders: 1234 shipped with an ETA of September 28, 5678 is processing with an ETA of October 2, 9999 is already delivered. The chips are what the evaluators print.

Turn 1 — the call goes right

Priya — Where is my order 1234?

Transcript (simulated) — “Where is my order 1234?”

Agent — Order 1234 has shipped. It is arriving on September 28.

Pass · Transcript Accuracy Pass · Intent Accuracy — order_status Pass · Tool Selection — get_order(1234)

Every link held, so every rule passed. Now break one link on purpose.

Turn 2 — one mis-heard digit

This is the classic voice failure. Priya says “1234”, the speech step returns “12340”, and now the agent is looking up an order that does not exist. This project's transcription step is simulated and returns the text unchanged, so it cannot mis-hear on its own — instead the wrong_arguments fault corrupts the extracted order id after extraction (1234 → 12340), which is exactly the state a mis-heard digit leaves the system in. You get to watch the rule fire without needing a microphone:

Priya — Where is my order 1234?

Agent (fault: wrong_arguments) — calls get_order(order_id="12340") → order not found → “I couldn't find that order.”

Fail · Tool Arguments — expected 1234, got 12340 Fail · Response Quality — no “shipped”, no “September 28”

Turn 3 — a friendly promise nobody made

The tool result for order 1234 says shipped, ETA September 28. The agent gets everything right and then adds one reassuring word:

Priya — When will it get here?

Agent (fault: unsupported_claim) — Order 1234 has shipped. It will arrive tomorrow.

Pass · Tool Selection — get_order Fail · Groundedness — “tomorrow” is not in the tool result

Groundedness scans the reply for words that make factual claims — shipped, delivered, processing, tomorrow, today — and requires each one to appear in what the tool actually returned. “Tomorrow” does not, so the rule fails even though the rest of the call was flawless. The related hallucinated_response fault is blunter: it claims delivered/tomorrow no matter what the tool said.

What the actual project demonstrates

voice-agent-evals/ is a deterministic, simulated voice support agent: no real microphone, no real speech-to-text, no text-to-speech — transcription simply returns the input. It uses the same three tools and the same four intents as the chatbot project, and the same ten-case dataset: stt-basic, stt-accent, intent-status, intent-cancel, intent-refund, tool-selection, tool-arguments, task-completion, missing-order recovery, and unknown-intent reliability — judged by the same eight rules.

The Scenario Lab runs ten preset scenarios, and there are nine fault modes in total: normal plus eight breakages. Each breakage names the evaluator that is supposed to catch it:

Fault injected Detecting evaluator
Wrong Tool Selection Tool Selection
Wrong Tool Arguments Tool Arguments
Hallucinated Response Groundedness
Unsupported Claim Groundedness precision check
Tool Failure Response Quality
Missing Information Reliability
Wrong Intent Intent Accuracy
Slow Response — real 250 ms delay vs a 100 ms budget Latency

The documented baseline run

The command-line runner, run_evals.py, builds a test suite from the ten cases, runs the agent against each one, and prints a scorecard. The project's documented baseline run looks like this:

Metric Documented baseline
Test cases passed 10 / 10
Intent accuracy 4 / 4
Transcript accuracy 2 / 2
Latency threshold 10 / 10
Required tool 2 / 2
Tool arguments 1 / 1
Response checks 5 / 5

That is a recorded run of the project's own test suite, not a live claim about this page — and the project says so itself about the latency row: the simulated agent uses no external services, so its local timings are not production voice-agent timings.

What you can open and click

The Scenario Lab in the dashboard calls a FastAPI Evaluation API — voice-agent-evals/server.py on port 8001, with /evaluate, /scenarios, /runs, and /stats. History is kept in memory with no database, so a restart clears it. Every result shown in the browser is computed by the real pipeline on the server: nothing is faked client-side, and a fault you inject is a fault the evaluators actually see.

Limitations

Four honest caveats, in plain words. Speech recognition is simulated — transcription just returns the input — so this project proves nothing about how a real recogniser handles noise, accents, or a toddler in the background. Intent detection is keyword-based and deterministic: fast and reproducible, but easily fooled by an unusual phrasing. The dataset is ten synthetic cases, not a sample of real calls. And local latency is not production latency.

Simulated voice path. There is no microphone, no real STT, and no TTS anywhere in this project. The 100 ms latency budget and the 250 ms injected delay are measured against a local mock, so they demonstrate that the Latency rule fires — not that a production call centre would meet or miss a target.

Takeaway

A voice call is a chain. Give every link its own rule, break each link on purpose to prove its rule fires, and a failed call stops being “it didn't work” and becomes “link three broke” — which is the difference between a mystery and a bug report.

Run it from the repository root: python voice-agent-evals/run_evals.py prints the baseline scorecard · python voice-agent-evals/server.py starts the Evaluation API on port 8001 for the Scenario Lab · the dashboard itself opens statically without it.
