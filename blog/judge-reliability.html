Judging the Judge: Building LLM-as-a-Judge Evaluations That Stay Honest

Engineering · 7 min read agentic_evals

Somewhere between the trace and the verdict sits the component that is hardest to get right and easiest to get wrong: the judge. This post is about how the evaluation engine builds a large language model judge that reads a trace, applies a written rubric, and returns a defensible pass or fail.

Why a judge at all

Deterministic assertions are wonderful when the behaviour can be expressed as data. They are also insufficient for open-ended work: did the answer help the user, was it helpful and honest, did it follow the plan. Those questions are judgement questions, and judgement questions need a judge.

The engine's answer is a rubric scorer: a language model that reads the trace and the written expectation, then returns a pass or fail with an explanation. The judgement is explicit rather than implicit, because the expectation was written down before the run.

What the judge reads

The judge consumes the trace - the spans, the tool calls, the outputs - together with the expectation. That grounding matters. A judge that scores an answer without being able to see what the tools actually returned is guessing. The engine's groundedness evaluator takes the claims inside the answer and checks them against the real tool results, so the judge is not scoring against memory.

This is the difference between a judge that can be wrong for a boring reason and one that can be wrong for a fixable reason. Groundedness turns an unverifiable claim into a checkable one.

Writing the rubric

A rubric is only as good as the criteria behind it. The engine expresses criteria as checks against the trace and the expectation, and each check maps to a score with a threshold and a required flag. Writing the rubric means writing down what good looks like in observable terms, before any answer is judged.

The practical rule that came out of the work: one judge per failure. When a run fails, the explanation should point at the specific criterion that failed, not at the answer as a whole. That is what makes a failed evaluation actionable.

Keeping the judge honest

A judge is a model, so it inherits the failure modes of models: sycophancy, self preference, verbosity bias, position bias. None of those are bugs in the engine, but they are risks to the evaluation. The mitigation is not to stop using a judge; it is to test the judgement the way you test anything else.

The engine's fault injection is the same discipline applied one level up. Break a stage of the agent on purpose, watch the matching evaluator fire, and confirm the judgement holds. A judge that cannot be made to fail on a known-bad run is not a judge, it is a rubber stamp.

Lessons

  • Judgement should be explicit. A written rubric beats an implicit instinct.
  • Ground the judge. Give it the trace, not just the answer.
  • Test the judgement. Fault injection is how you prove the rule fires.
  • Separate the judge from the decision. Scoring produces evidence; gates decide.

Takeaway

A judge is a model, so treat it like one: give it a precise rubric, ground it in the trace, and test it like any other component. The moment the judgement is trusted without being checked, the evaluation has stopped being a measurement and started being a performance.

Run it from the repository root: agentic-evals run discovers and runs every eval file in the current directory - the rubric scorer is one of the scorer implementations behind the engine, and the fault injection that proves a judgement fired lives in the use case projects.
