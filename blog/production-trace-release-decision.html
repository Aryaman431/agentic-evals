From Production Trace to Release Decision

Beginner · 9 min read Production trace to release decision

Sam wants to change how a financial assistant reasons and ship it this week. “I think this is better” is not a decision, and neither is a gut feeling about a demo. This article follows one recorded run all the way to a verdict with written thresholds — READY, NEEDS REVIEW, or NOT READY — and shows exactly which number decided it.

The problem

Sam maintains a financial assistant — the kind of tool that reads your spending and explains it in plain language. One run in production looked odd: the assistant was asked why there was a $2,847 charge from NORTHWIND SUPPLY on a card, and it had to look the charge up, compare it to the person's history, and answer without inventing anything.

Sam now wants to change how the assistant reasons: a tighter explanation template, a smarter model, better handoffs between the parts of the system. Every one of those changes sounds like an improvement in the meeting. The problem is that “sounds better” and “is better” are different claims, and the second one needs evidence.

There are three bad ways to answer this question. Ship it and hope — then find out from customers. Ask the team to eyeball a few outputs — which measures whoever happened to be watching. Or run the new version once, see a good number, and declare victory — which measures nothing, because you do not know what the old version would have scored on the same run.

The missing piece is always the same: a reference point. Without knowing what the current system scores, any number from the new system is just a number. And without a rule written down in advance, any judgement about that number is just an opinion with a decimal point.

The approach: record, save, replay, compare

The fix is an old engineering habit applied to AI systems: keep the last known-good measurement, run the change against the same scenario, and compare the two with thresholds you agreed on before you looked at the results. Four words carry the whole method:

  • Trace — a recorded timeline of one run: the question that came in, the tools that were called, what they returned, and the answer that went out, in order. In this project the trace is one run of the financial assistant explaining that unusual $2,847 expense. A trace is also the raw material of a test case — one input plus the behaviour we expect back — because it captures a real situation worth replaying.
  • Baseline — the current system's scores on that scenario, saved as the reference point for every later comparison. Six metrics are recorded, so the baseline is a profile, not a single number that can hide a collapse in one dimension.
  • Proposed change — the thing Sam wants to ship. This project offers three: prompt_update (new instructions), coordination_update (new teamwork logic between parts), and model_change (a different model).
  • Replay — running the same scenario again with the change in place, then comparing the new numbers metric by metric against the baseline. Same input, same scenario, one variable changed: that is what makes the difference attributable to the change.

Then the last piece, and the one that removes the argument: a threshold — a number written down in advance that decides what counts as good enough. “Improved overall” is not a rule. “Overall delta of at least +2.0 with no metric regressing more than −3.0” is a rule, and it can be checked by code at 2 a.m. without anyone's mood involved.

Notice what this buys. The comparison is against a saved reference instead of a memory. The thresholds exist before the numbers do, so the verdict cannot be reverse-engineered from the result. And because six metrics are checked separately, a change that improves the average while quietly wrecking one dimension gets caught instead of averaged away.

How the evaluation works

The walkthrough has five stages. The production trace is captured, exported as an AI Ops Spec (a JSON file describing the run so it can be reused), scored as a baseline, replayed with a proposed change, and then compared — which produces the release decision.

Six metrics are scored at baseline and again after the replay:

  • response_quality — clarity, accuracy, and grounding of the answer
  • task_completion — whether the user's goal was actually satisfied
  • tool_correctness — whether tool arguments and results stayed faithful
  • agent_coordination — handoff quality and shared context between parts
  • safety_compliance — policy adherence and guardrail coverage
  • performance — end-to-end latency against a 1.5 s target

The decision itself is three ordered gates, checked in this exact order. The thresholds are returned verbatim inside every comparison payload, so you can read the rule next to the number it judged:

Verdict Condition
NOT READY Overall delta ≤ −2.0 or any metric delta ≤ −8.0 or post-replay safety < 70 or any metric < 60
READY Overall delta ≥ +2.0 and worst-metric regression ≥ −3.0 and post-replay safety ≥ 80 and post-replay overall ≥ 78
NEEDS REVIEW Everything else — nothing hard-failed, but a readiness gate was missed

The order matters. The hard fails are checked first, so a catastrophic regression cannot be rescued by a good average. Only if nothing failed does the READY gate get its turn, and it demands all four of its conditions. Anything left over lands in NEEDS REVIEW, which is the honest answer for “this needs a human”.

  1. 01 Trace One recorded run of the current agent, explaining the $2,847 charge. →
  2. 02 Baseline Today's six metric scores, saved as the reference. →
  3. 03 Proposed Change Prompt, coordination, or model — pick exactly one. →
  4. 04 Comparison Replay the scenario and compare metric by metric. →
  5. 05 Release Decision READY, NEEDS REVIEW, or NOT READY — computed from the written thresholds.

A simple example

Here is the whole method in one table. The baseline column is the project's documented demo baseline for the six metrics; the replay column applies the project's documented base deltas for a prompt_update. (The demo adds ±1 hash jitter to each delta and ±2 to the baseline, so your own run may show a neighbouring number — the arithmetic below is the jitter-free version, which is what makes the logic easy to follow.)

Metric Baseline Replay Delta
response_quality 82 90 +8
task_completion 85 90 +5
tool_correctness 78 79 +1
agent_coordination 74 76 +2
safety_compliance 86 86 0
performance 71 70 −1
Overall (mean of six) 79.3 81.8 +2.5

Fig. 03 — worked example from the project's documented base values, before hash jitter

Now run the four READY gates against those numbers:

  • Overall delta +2.5 ≥ +2.0 — pass
  • Worst-metric regression −1 ≥ −3.0 (performance) — pass
  • Post-replay safety 86 ≥ 80 — pass
  • Post-replay overall 81.8 ≥ 78 — pass

All four, so the verdict is READY, and it ships with a plain-language recommendation: approve the release, because the replay shows measurable gains and clears every readiness gate.

The other two change types are where the method earns its keep. Watch what happens when a change improves the average but hurts one dimension:

Change Overall delta Worst regression Post-replay safety Verdict
prompt_update +2.5 −1 (performance) 86 READY
coordination_update +2.7 −4 (performance) 85 NEEDS REVIEW
model_change +1.0 −10 (safety_compliance) 76 NOT READY

Fig. 04 — the three documented demo outcomes, jitter-free

Demo outcomes at a glance

prompt_update → READY coordination_update → NEEDS REVIEW model_change → NOT READY

coordination_update has the best overall delta of the three and still gets a worse verdict than prompt_update, because one metric regressed by −4 and the READY gate requires every regression to stay within −3.0. Averaging would have hidden that. And model_change is blocked outright: its safety metric drops by −10, which breaches the −8.0 hard fail on its own — no good average can rescue it. That is the difference between a rule and an opinion.

What the actual project demonstrates

The project lives in Production trace to release decision/ and is deliberately small: no React build, no Node, no Docker — one HTML file and an optional Python backend.

  • A self-contained frontend. The whole five-stage walkthrough — trace, AI Ops Spec, baseline, replay, decision — is a single file that works when you open it directly in a browser. Nothing is fetched, nothing is compiled.
  • Three change types. prompt_update tightens the explanation template with merchant context and a prior-charge reference; coordination_update improves the planner handoff by enriching shared context; model_change swaps the analyst model for a stronger reasoning variant.
  • Thresholds returned verbatim. Every comparison payload carries the readiness gates alongside the numbers, plus a plain-language recommendation: approve, hold for human review, or block the release.
  • An optional backend that really works. app.py is a FastAPI service with Supabase persistence. When SUPABASE_URL and SUPABASE_SERVICE_ROLE_KEY are set it genuinely stores and serves runs; without them it falls back to in-memory demo mode with identical endpoints. The service-role key stays server-side — it is never sent to the browser.

The five stages you click through are Production Trace → AI Ops Spec (the JSON export) → Baseline Evaluation → Simulated Replay → Release Decision, and the baseline scores are deterministic demo values — 82, 85, 78, 74, 86, 71 across the six metrics, jittered by ±2 from a hash of the scenario id, so the same scenario always produces the same story.

Limitations

Read the numbers as a demonstration of a method, not as a measurement of a real system. The value of this project is the shape of the argument — record a run, save a baseline, replay with one change, compare against thresholds you wrote down first — and that shape works whether the numbers come from a demo or from a real evaluation. The numbers here come from a demo.

Simulated demo data. The production capture is simulated demo data, the AI Ops Spec is a representative example rather than a real AgenticLens export, and the replay is simulated: the scores come from documented deterministic demo logic, no real agent application is rerun, and the scores are illustrative — they were not produced by the agentic-evals framework. This page makes no claim of a live production integration.

Takeaway

A saved baseline plus thresholds written down in advance turns “I hope this helps” into a decision you can defend: compare against a reference, check every metric separately, and let one bad regression block the release even when the average went up. Labelling what is simulated is part of the rigor, not a footnote to it.

Run it locally: open Production trace to release decision/index.html directly — it is fully self-contained · optional backend: cd "Production trace to release decision" then uvicorn app:app --reload (port 8000, in-memory demo mode until SUPABASE_URL and SUPABASE_SERVICE_ROLE_KEY are set).
