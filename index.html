01 · Chatbot Evaluation

Chatbot Evaluation

Maya ordered a birthday gift for her sister. The delivery date passed. She opens the company’s support chat and asks, “Where is my order 1234?” — then, annoyed, “I want a refund for order 1234.” The chatbot answers instantly and confidently. It sounds perfect. But did it actually check her order, or just invent something plausible?

A chatbot agent does not only write sentences. It decides, then acts: it picks a tool — a small program it is allowed to call, like checking an order or issuing a refund — reads whatever comes back, and writes the reply. Every one of those steps can go wrong.

What can go wrong

  • It calls the wrong tool. Maya asks to cancel, and the agent only checks the delivery status.
  • It misreads the order number. 1234 quietly becomes 12340.
  • It invents a result. “Your refund was processed yesterday” — without ever checking.
  • It appends a promise. “It will arrive tomorrow,” a claim no data supports.
  • It takes too long. The answer lands after she has already closed the tab.
  • It guesses. When she forgets the order number, it should ask — not invent one.

Why one good answer is not enough

One reply proves one path. The agent can answer her first question perfectly and still mishandle the cancellation, the refund, or the message that arrives with no order number at all. A single answer shows that one route works; a suite of test cases covers many.

How test cases help

A test case is one input plus the behaviour we expect back. For Maya’s refund, the expected intent — what the agent concludes the user wants — is refund_order, the required tool is refund_order, and the reply must contain the word “refund”. The expectations are written down before the run, so the answer gets judged instead of admired.

The project ships 10 cases: stt-basic, stt-accent, intent-status, intent-cancel, intent-refund, tool-selection, tool-arguments, task-completion, missing-order, unknown-intent.

How wrong behaviour gets caught

Eight rules — evaluators — judge every run: Transcript Accuracy, Intent Accuracy, Tool Selection, Tool Arguments, Response Quality, Groundedness, Reliability, and Latency. Each one returns pass or fail with a short explanation of why. Fault injection then deliberately breaks one stage of the agent on purpose, to prove that the matching rule actually fires.

What the project actually builds

A simulated text support agent. A Chat Playground where a typed message posts to /chat/evaluate and comes back with the response, intent, tool, arguments, and latency. A Scenario Lab that runs scenarios live through Evaluation API → agent → evaluation → trace (a recorded timeline of the run) → metrics → dashboard, served by FastAPI Chatbot-eval/server.py on port 8001 with history kept in memory.

It also ships a view of the 10-case dataset. Groundedness that compares claims like “shipped”, “delivered”, or “tomorrow” against the tool’s real result. And a CLI — python run_evals.py — that prints a scorecard and exits with code 0 or 1.

Opened statically, the page shows an offline status until the backend is running. The mock orders are 1234 (shipped, ETA September 28), 5678 (processing, October 2), and 9999 (delivered).

Takeaway

One good answer proves one path. A suite of cases with explicit rules turns “sounds right” into “measured right” — and breaking the agent on purpose proves the checks actually fire.

02 · Voice Agent Evaluation

Voice Agent Evaluation

Priya calls the support line: “Where is my order 1234?” For the call to succeed the system must do four things in a row — hear her words, work out what she wants, pick and call the right action with the right order number, and say something true back. If any link breaks, the call fails.

  1. 01 Caller Speaks Priya says her line into the phone. →
  2. 02 Speech Recognition Her words become text — accents included. →
  3. 03 Intent The agent decides what she is asking for. →
  4. 04 Action It calls the right tool with the right order number. →
  5. 05 Evaluation Eight rules check every link in the chain.

Every stage can fail. The words can be mis-heard, accents included. The intent label — what the agent concludes the caller wants — can be wrong: order_status, cancel_order, or refund_order. The agent can pick the wrong tool (a small program it is allowed to call), or corrupt the order id, or invent claims. The reply can be slow.

An out-of-scope request — “tell me something interesting” — must be declined without calling any order tool at all. And when the order number is missing, the agent must ask for it instead of guessing.

What the project actually builds

A deterministic simulated voice support agent — no real microphone, no real speech-to-text, no text-to-speech — plus 10 test cases (2 STT including an accent, 3 intent, tool selection, tool arguments, task completion, missing-order recovery, and unknown-intent reliability), judged by the same eight rules.

A CLI baseline, run_evals.py, prints a scorecard. The project’s documented baseline run reports 10/10 passing — intent 4/4, transcript 2/2, latency 10/10, required tool 2/2, tool args 1/1, response checks 5/5. That is a recorded run of the project’s own test suite, not a live claim about this page.

A Scenario Lab in the dashboard calls a FastAPI Evaluation API (voice-agent-evals/server.py, port 8001; /evaluate, /scenarios, /runs, /stats; history in memory, no database). The results are computed by the real pipeline — nothing is faked in the browser.

Takeaway

A voice call is a chain — evaluate every link so a failed call tells you which link broke, not merely that it broke.

Fault → evaluator

Testing finds where it broke

Ten preset scenarios each inject one fault and name the evaluator that catches it:

  • Wrong Tool Selection → Tool Selection
  • Wrong Tool Arguments → Tool Arguments
  • Hallucinated Response → Groundedness
  • Unsupported Claim → Groundedness precision check
  • Tool Failure → Response Quality
  • Missing Information → Reliability
  • Wrong Intent → Intent Accuracy
  • Slow Response — a real 250 ms delay against a 100 ms budget → Latency

Honest note. Speech recognition is simulated (transcription just returns the input), intent detection is keyword-based and deterministic, the dataset is small and synthetic, and local latency is not production latency.

03 · Production Trace to Release

From Production Trace to Release Decision

Sam maintains a financial assistant that explains people’s spending. She wants to change how it reasons and ship it — but what if the change quietly makes it worse? Guessing is not a decision. Here is how a recorded run, a saved baseline, and a replay turn “I think this is better” into an answer she can defend.

  1. 01 Trace One recorded run of the current agent. →
  2. 02 Baseline Today’s six metric scores, saved as the reference. →
  3. 03 Proposed Change Prompt, coordination, or model — pick one. →
  4. 04 Comparison Replay the scenario and compare metric by metric. →
  5. 05 Release Decision READY, NEEDS REVIEW, or NOT READY — from written thresholds.

Trace

A trace is a recorded timeline of one real run — the steps the agent took, in order. In this project it is a financial assistant explaining an unusual expense of about $2,847.

Baseline

A baseline is the current agent’s scores, saved as the reference point for every later comparison. Six metrics are recorded: response quality, task completion, tool correctness, agent coordination, safety compliance, and performance.

Proposed change

The proposed change is the thing Sam wants to ship. She picks one of three: prompt_update (new instructions), coordination_update (new teamwork logic), or model_change (a different model).

Replay and comparison

A replay runs the same scenario again with the change in place, then compares the new numbers metric by metric against the baseline.

Release decision

The release decision is computed from written thresholds, not from a feeling. READY needs an overall delta of at least +2.0 and a worst-metric regression no worse than −3.0 and post-replay safety of at least 80 and post-replay overall of at least 78. NOT READY when the overall delta is −2.0 or worse, or any metric delta is −8.0 or worse, or post-replay safety is below 70, or any metric is below 60. Everything else is NEEDS REVIEW. In the demo, prompt_update → READY, coordination_update → NEEDS REVIEW, and model_change → NOT READY.

The walkthrough has five stages: Production Trace → AI Ops Spec (a JSON export) → Baseline Evaluation → Simulated Replay → Release Decision.

What the project actually builds

A fully self-contained single-file frontend that works when you open it directly. An optional FastAPI app.py with Supabase persistence that is genuinely functional when the Supabase environment variables are set, and in-memory demo mode otherwise. The thresholds are returned verbatim inside the comparison payloads, and every verdict comes with a plain-language recommendation.

Takeaway

Comparing a change against a saved baseline with written thresholds turns “I hope this helps” into a decision you can explain — and labelling what is simulated is part of the rigor.

SIMULATED DEMO DATA. The production capture is simulated demo data, the AI Ops Spec is a representative example rather than a real export, and the replay is simulated: the scores come from documented deterministic demo logic, no real agent application is rerun. The scores are illustrative and were not produced by the agentic-evals framework. This page makes no claim of a live production integration.
