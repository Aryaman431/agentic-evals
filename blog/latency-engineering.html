The 100ms Budget: Latency Engineering for Real-Time Agents

Engineering · 6 min read voice-agent-evals

A voice call has a clock running on it from the moment the caller speaks. This post is about the discipline of latency budgets - what to measure, how to set the number, and how to prove the measurement means something.

Latency is a quality attribute, not a number

For a chatbot, a slow answer is a annoyance. For a real-time agent, a slow answer is a failed answer. The user has already waited; the context has moved on; the moment of confidence is gone. Latency has to be treated as a first-class quality attribute, and the only way to treat it that way is to put a number on it before the run starts.

The engine models this with a latency ceiling on the test case and a latency evaluator that checks the run against it. The ceiling is not a suggestion that the runner hopes is satisfied; it is a threshold that produces a score and, through the gate, a verdict.

Setting a budget

Budgets are written before the runs, not after them. A team that sets a latency target after seeing a number will always ship to the number it saw. A team that sets a budget before the agent exists has something to design against, and something to test against.

The work went up the stack: the agent, the tools, the orchestration, the transport. Each layer could move, and each layer needed its own number. The budget is the forcing function that keeps those conversations concrete.

Measuring honestly

A latency number is only useful if it is measured where it will be used. The engine's evaluation runs against a simulated agent, on local hardware, with local mocks for the parts that would otherwise be external. That is the right way to test the logic of the system; it is not the right way to claim anything about a production voice pipeline.

The honest version of the practice is to label what is simulated and what is real, and to keep the two separate in any report. A green latency score on a simulated run is a green score about the simulation, not about the phone network.

Proving the rule fires

The latency evaluator earns its keep in one specific way: through fault injection. A fault can insert a real delay into the timed section, and the evaluator then has to decide whether the run met the budget. The injected delay is real, the clock is real, and the judgement is mechanical. That is the whole test, and it is a good one.

The lesson is not about latency specifically. It is about the general discipline the engine applies everywhere: write the expectation, run the system, break it on purpose, and confirm the check catches the break. Latency was just the first place where that discipline had a number that mattered.

Lessons

  • Budgets are promises made before the run and checked after it.
  • Measurement must be honest about what it is measuring.
  • Fault injection is the cheapest way to prove a check is real.
  • Latency budgets should be set per layer, not per system.

Takeaway

A latency budget is a promise you make before the run and keep after it. Set the number, measure it honestly, and prove the check fires - then a real-time agent has something to ship against instead of something to hope for.
